# BOT 闪光致盲概率整体提升方案

日期：2026-09-11  
工作区：`E:\CS2AS05`  
范围：仅 BOT 闪光弹的“选择与回放概率”，不修改其他道具系统行为

## 调查结论

当前 BOT 被闪白的最终机会，不是单一概率，而是多个条件串联：

1. 闪光投掷点必须进入 BOT 的触发区域，BOT 仍需存活且回合未结束。
2. `normal`、`more`、`less` 模式会检查 BOT 是否朝向投掷方向；`max` 对闪光仍要求至少存在一个可被闪白的敌人。
3. `EvaluateFlashTargets` 以闪光落点到敌方眼睛的角度和世界几何视线判断 `BlindableEnemies`。角度约束为水平 ±53°、垂直 ±45°，视线必须无遮挡。
4. 只要没有可闪敌人，闪光不会被回放；这部分是有效性保护，不应删除。
5. 对“可闪敌人占全部敌人的比例”，当前代码再映射一次回放概率：

| 可闪敌人 / 敌人总数 | 当前回放概率 |
| --- | ---: |
| 1 / 5 | 10% |
| 1 / 4 | 20% |
| 1 / 3 | 30% |
| 1 / 2 | 60% |
| 2 / 5 | 50% |
| 2 / 4 | 60% |
| 2 / 3 | 80% |
| 3 / 5 | 70% |
| 3 / 4 | 90% |
| 4 / 5 | 100% |
| 全部 | 100% |

6. `normal`、`less`、`more` 还有一层信息门槛：当没有可闪目标掌握该 BOT 信息时，`normal`/`less` 的闪光概率为 80%，`more` 为 100%。因此 `more` 目前已经没有信息门槛损失，主要损失来自上面的目标比例映射。
7. 进入闪光区域后有 12 秒比例窗口；窗口内继续使用上一次比例随机判定。另有上游投掷冷却、队伍/计划检查、失败概率冷却和每回合弹药/购买条件。这些应保留，不能把“提高被闪白概率”误做成取消所有投掷约束。

## 问题定位

当前模型对“只有一个敌人处于有效闪光视线”的场景过于保守。实际 BOT 对局中，敌人经常分散在不同房间、楼层或掩体后，`1/5`、`1/4`、`1/3` 并不代表闪光没有价值，只代表当前落点能照到其中一部分敌人。10% 至 30% 的二次随机门槛会让大量有效闪光根本不生成，最终表现为 BOT 很少把敌人闪白。

因此首要改动点是 `GetFlashRatioThreshold`，而不是修改闪光弹实体创建、闪光持续时间或地图投掷数据。

## 推荐方案

实施状态：第一阶段已按本方案落地到工作区候选，尚未完成真实 CS2 回合验收。

### A. 提高比例映射的下限和斜率

建议将当前比例映射调整为以下候选值：

| 可闪敌人 / 敌人总数 | 当前 | 推荐候选 | 目的 |
| --- | ---: | ---: | --- |
| 1 / 5 | 10% | 40% | 单个有效目标也有稳定机会触发 |
| 1 / 4 | 20% | 50% | 降低分散站位造成的过度损失 |
| 1 / 3 | 30% | 60% | 让有效闪光成为常态而非偶发 |
| 1 / 2 | 60% | 75% | 保留目标数量差异 |
| 2 / 5 | 50% | 65% | 两个有效目标应明显提高机会 |
| 2 / 4 | 60% | 75% | 与 1/2 的有效比例一致 |
| 2 / 3 | 80% | 85% | 接近稳定触发 |
| 3 / 5 | 70% | 80% | 三个目标时减少随机落空 |
| 3 / 4 | 90% | 95% | 几乎必然回放 |
| 4 / 5 | 100% | 100% | 保持原行为 |
| 全部 | 100% | 100% | 保持原行为 |

推荐优先采用 A，不新增配置项，不新增 `bot_nades` 模式，不修改上游 `more`/`normal`/`less` 的名称和语义。它只提高已确认“至少有一个敌人可被闪白”的闪光回放概率。

### B. 不采用的激进方案

以下方案暂不采用：

- 所有可闪光都强制 100% 回放：会放大错误视线判定、重复闪光和无效投掷。
- 删除角度判断或世界视线判断：会导致隔墙、背向或明显不可见的敌人被错误计为目标。
- 修改闪光持续时间、致盲强度或 `CFlashbangProjectile` 参数：这属于游戏效果层，不是 BOT 投掷选择层，且会偏离当前上游道具系统边界。
- 恢复此前已删除的 5 秒 BOT 间隔、队伍间隔或自定义每回合上限：会与“恢复上游原版道具系统”的既定目标冲突。
- 只把 `normal`/`less` 的信息概率从 80% 调到 100%：对 `more` 没有收益，无法解决主要问题。

- 源码和构建输入中不存在 `NadePacingPolicy` 接入；
- 五档 `bot_nades` 契约不发生变化。

由于当前函数是插件私有方法，优先将概率表抽取为无副作用的私有静态函数，或使用现有上游测试结构覆盖；不要引入新的运行时配置存储。

### 真实 CS2 验收

由用户在相同地图、相同 BOT 数量和相同回合条件下，对比旧候选与新候选：

1. `bot_nades more`：记录至少 20 个有可闪目标的闪光触发机会，以及实际生成数量和 `player_blind` 数量。
2. `bot_nades normal`：确认整体闪光触发增加，但没有无目标乱投。
3. `bot_nades less`：确认闪光增加来自比例概率调整，不是恢复额外节奏限制。
4. `bot_nades max`：确认有可闪目标时保持积极投掷，0 个可闪目标时不生成闪光。
5. 至少记录每次测试的地图、BOT 数量、模式、可闪目标数、闪光生成数、实际被闪人数和控制台日志。

建议以“有效闪光率”作为主要指标：

```text
有效闪光率 = 产生至少一个 player_blind 事件的闪光数 / 生成的闪光总数
```

目标不是单纯提高生成数，而是让有效闪光机会明显增加，同时有效闪光率不出现明显下降。候选阶段可先以整体 `player_blind` 事件数提升 30% 至 100% 作为观察区间，不预先承诺固定百分比。

## 验收门槛

只有满足以下条件，才可称为方案实施完成：

- `1/5`、`1/4`、`1/3` 等低覆盖场景的回放概率按候选表提高；
- 没有可闪目标时仍不回放；
- 视线、角度、朝向、回合、经济和上游冷却条件没有被删除；
- `max`、`more`、`normal`、`less`、`off` 的既有契约不变；
- 没有重新引入 BOT/队伍投掷节奏限制；
- NadeSystem 构建和内置资源完整性校验通过；
- 真实 CS2 对照中 `player_blind` 事件明显增加，且没有明显的隔墙闪、无目标闪或异常刷闪；
- 真实游戏验收通过前，候选不得称为正式版本，不得覆盖已发布的 0.5.13 安装器、夸克分享或更新 feed。

## 风险与回滚

主要风险是有效闪光变多后，BOT 可能在部分地图的窄小区域连续投掷，或者因地图投掷点视线数据偏差出现低质量闪光。出现以下任一情况，应停止发布：

- 无可闪目标时仍大量生成闪光；
- `player_blind` 没有增加但闪光生成量异常增长；
- 出现明显隔墙闪、穿实体闪或自残/友伤异常；
- 影响烟雾、燃烧弹、手雷或回合结束清理；
- 与上游 NadeSystem 行为边界发生额外偏离。

回滚只恢复候选工作区中的 NadeSystem DLL、deps、pdb 和对应摘要，不覆盖已发布资源，不使用破坏性 Git 操作。

## 最终建议

先实施 A 方案，以 40% 作为单目标最低概率、以 100% 作为高覆盖上限。该方案改动面小、可解释、容易通过统计验证，并且保留“必须存在真实可闪目标”的安全边界。真实回合数据证明仍然偏低后，再考虑对角度阈值或 12 秒窗口做第二阶段单独实验；这两项不应与第一阶段同时改变。
