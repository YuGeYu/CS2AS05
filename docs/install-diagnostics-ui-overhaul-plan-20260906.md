# 安装与诊断页面整体改版方案

> 状态：调查完成，待实施
> 日期：2026-09-06
> 范围：`src/views/InstallView.vue` 及其页面专属样式、必要的页面测试

## 1. 调查结论

### 当前实现

页面由以下同级区域组成：

1. 页面标题、版本和主题设置。
2. `SupportActions`：更新、官网、意见、赞助、关于与来源。
3. CS2 目录选择与扫描。
4. 目录、CS2、插件三项状态。
5. 开机启动设置。
6. 定制资源包安装/覆盖更新。
7. 原版 Panel 入口。
8. 清除数据、提交故障、官网账号、卸载插件。
9. 卸载、清除数据、故障提交、账号登录四类模态框。

页面逻辑和真实能力已经比较完整，关键操作由 Pinia `useCs2Store`、Tauri support service 和 `SupportActions` 提供，不能通过纯 UI 假装增加状态或改变安装契约。

### 主要问题

| 问题 | 证据 | 影响 |
| --- | --- | --- |
| 主路径不突出 | 安装区域在更新、目录、设置之后才出现；所有区块都是同级纵向流 | 新用户不知道先选目录还是先安装 |
| 状态与动作分离 | 三项状态独立于目录和安装区，状态没有统一的“下一步” | 用户需要自己把状态翻译成操作 |
| 页面密度不均 | 顶部支持操作占用首屏，危险维护操作与普通维护操作并列 | 重要操作被稀释，卸载误触风险较高 |
| 诊断语义不足 | 当前状态主要是“目录/CS2/插件”三个短标签，缺少“可安装/需退出/需选择目录”等明确结论 | 出错时恢复路径不直观 |
| 移动端只是堆叠 | `@media (max-width: 640px)` 将区域全部改成单列，缺少主次折叠策略 | 375px 页面过长，关键按钮需要滚动寻找 |
| 异步反馈分散 | `maintenanceState`、store toast、模态框状态各自显示 | 用户难以判断当前操作是否仍在进行 |
| 操作反馈不够细 | 安装按钮有文字变化，但目录扫描、Panel 启动、账户和危险操作缺少统一的阶段反馈 | 等待期间容易重复点击或误以为失败 |

### 已有资产和约束

- 技术栈为 Vue 3 + Pinia + Tauri 2，页面已使用 Lucide 图标和原生 `button/input/select/textarea`。
- 全局设计令牌在 `src/styles/main.css`，已有浅色/深色主题、密度和圆角偏好，不应另起一套颜色系统。
- 现有设计契约要求保留语义控件、键盘焦点、响应式断点、`prefers-reduced-motion` 和中文界面。
- `clearAssistantData()` 只允许清理助手缓存、日志和 WebView 偏好；不应改变 CS2 文件、插件、Demo 或复盘数据库边界。
- `setAssistantAutostart()` 为 HKCU Run，无需管理员权限；页面文案应继续明确这一点。
- 故障单会自动附带脱敏诊断信息；页面不能暗示会上传 Demo、游戏文件、皮肤配置或密码。
- 当前 `useCs2Store` 使用 `localStorage` 持久化选中目录，且清除数据流程调用 `localStorage.clear()`；这与本项目“除网站缓存外不使用 localStorage”的约束存在冲突。改版实施时应先把目录选择持久化迁移到 Tauri 应用数据/现有原生偏好接口，再调整清除范围，不能把这项现状继续包装成 UI 优化完成。

## 2. 设计方向

### 核心模型

改为“诊断结论驱动的工作台”，首屏只回答三件事：

1. 当前是否已经选中有效 CS2 目录。
2. 当前是否可以安装或覆盖更新。
3. 用户下一步应该点击什么。

把页面组织为“顶部总状态 + 主任务卡 + 辅助任务区 + 危险操作区”，而不是继续增加长列表卡片。

### 视觉策略

- 延续当前蓝色主色、青玉/青绿色状态色、青铜强调色和深色主题；不采用 UI/UX Pro Max 检索到的粉色 Pixel Art 推荐，因为它与现有桌面工具语义和既有令牌不一致。
- 使用紧凑的工作台密度：8px 间距节奏、单一主 CTA、细边框和轻阴影，避免营销式大卡片和装饰性背景。
- 让“当前结论”使用较大字号，让辅助说明使用稳定的二级文字；颜色不能作为唯一状态标识，必须同时有文字和图标。
- 保持卡片圆角不超过现有系统上限；不在卡片内嵌套卡片。

## 3. 目标信息架构

### 顶部状态头部

- 左侧：`安装与诊断`、一句当前结论，例如“可以开始安装”或“请先退出 CS2”。
- 右侧：版本号、主题设置、刷新诊断。
- 下方：四个紧凑状态节点：目录、CS2、插件包、Panel；每个节点有图标、短结论和可选动作。
- 状态节点不再只显示“已选择/未选择”，要映射到明确的状态文案：
  - `未选择目录`：选择目录
  - `目录有效`：可继续
  - `CS2 运行中`：退出 CS2
  - `插件已安装`：可覆盖更新
  - `检测失败`：重新检查

### 主任务区：安装资源包

- 置于首屏主视觉区域，保留当前版本和上游版本说明。
- 主 CTA 只保留一个：安装、覆盖更新或“先选择目录/先退出 CS2”，按钮文案随状态变化。
- 将“保留写前备份”变成主 CTA 下方的显式安全选项，并补充简短说明。
- 在按钮附近显示操作阶段：准备中、写入中、验证中、完成、失败；阶段信息使用 `aria-live`。
- 安装成功后展示下一步入口：打开 Panel 或前往人机预设，不自动跳转。

### 辅助任务区

采用桌面端双列、窄屏单列：

- **目录与环境**：目录路径、候选目录数量、选择目录、重新扫描；候选目录作为可展开列表显示，不在无候选时占空间。
- **助手偏好**：开机启动开关及当前保存结果；将低频设置放入折叠区，默认不抢主任务空间。
- **兼容入口**：原版 Panel 单独放在“高级兼容”折叠区，明确不能与本助手同时写入同一目录。
- **更新与支持**：`SupportActions` 改成紧凑工具栏，更新状态放在标题旁，官网/意见/赞助/来源保持可访问。

### 维护与危险区

- 默认折叠为“维护与求助”，显示提交故障和账号入口。
- “清除数据”和“卸载插件”放入危险区，视觉上分组但不使用夸张红色大面积背景。
- 卸载按钮必须继续受“已选目录 + 非忙碌”约束；清除数据必须保留现有确认文案边界。
- 故障提交和账号登录继续使用模态框，但统一对话框标题、关闭按钮、错误状态和底部动作顺序。

## 4. 组件与状态设计

### 建议的页面内部组件

优先在 `InstallView.vue` 内拆出可测试的局部组件或 render 区块，不立即引入全局抽象：

- `InstallDiagnosisHeader`：总状态和页面级操作。
- `EnvironmentStatusRail`：目录、CS2、插件、Panel 状态节点。
- `InstallActionPanel`：安装主 CTA、备份选项、阶段反馈。
- `DirectoryPickerPanel`：路径和候选目录。
- `SecondaryToolsPanel`：偏好、原版 Panel、更新支持。
- `MaintenancePanel`：故障、账号、清理、卸载。

如果拆组件会导致 Pinia/Tauri mock 复杂化，则保留单文件模板，仅按上述边界分组 class 和 computed；不为拆分而拆分。

### 状态矩阵

| 条件 | 顶部结论 | 主 CTA | 目录动作 | 安装动作 |
| --- | --- | --- | --- | --- |
| 无目录 | 需要选择 CS2 目录 | 选择目录 | 选择目录、扫描 | 禁用安装 |
| 目录有效、CS2 未运行、未安装 | 可以安装 | 安装定制插件包 | 重新扫描 | 可用 |
| 目录有效、CS2 未运行、已安装 | 可以覆盖更新 | 覆盖更新定制插件包 | 重新扫描 | 可用 |
| 目录有效、CS2 运行中 | 请先退出 CS2 | 退出 CS2 | 保留查看 | 禁用安装 |
| 任意状态、store busy | 正在处理 | 显示当前阶段 | 禁用重复操作 | 禁用重复操作 |
| 检测失败 | 环境检查失败 | 重新检查 | 重新扫描 | 禁用安装 |
| 安装失败 | 安装未完成 | 重试安装 | 查看诊断 | 恢复可操作 |

## 5. 响应式方案

- `>= 1100px`：页面最大宽度约 1120px；顶部状态横向排列；主任务区与诊断摘要并列；辅助区双列。
- `861-1099px`：主任务区单列，状态节点保持两行网格；支持工具栏允许换行。
- `641-860px`：目录、安装和状态区域保持清晰垂直顺序；兼容入口和偏好默认折叠。
- `<= 640px`：去除外层浮动壳体边框和大阴影；主 CTA 全宽；状态节点两列；辅助任务使用 `<details>`，危险区保持最后；按钮触控区域至少 44px。
- `375px`：路径输入必须省略显示但可通过 `title`/辅助文本读取；长按钮文字允许换行，不得挤压图标或造成横向滚动。
- 所有断点都要覆盖浅色、深色、紧凑密度、宽松密度和减少动效模式。

## 6. 无障碍与交互要求

- 页面主结论使用 `aria-live="polite"`；失败使用 `role="alert"` 或明确的 live 区域。
- 每个状态节点不仅依赖颜色，必须有文本、图标和可读的状态名称。
- 所有图标按钮保留 `aria-label` 和 `title`；模态框关闭后将焦点恢复到触发按钮。
- 折叠区域使用原生 `<details>/<summary>` 或等价的 `aria-expanded`，不使用不可访问的视觉点击容器。
- 安装、扫描、更新、登录、提交故障期间禁用重复提交，并显示明确进行时文案。
- 所有按钮补充 `:active` 的轻微 `scale(0.97)` 反馈；只过渡 `transform`、`opacity`、背景和边框颜色，不动画布局尺寸。
- 使用 150-220ms 的 `cubic-bezier(.23,1,.32,1)` 交互过渡；不为高频键盘操作添加延迟动画。
- `prefers-reduced-motion: reduce` 下取消状态节点移动和装饰动画，只保留即时状态变化。

## 7. 实施顺序

1. 先建立页面专属 class 和状态映射，不改 Tauri 命令、Pinia store 或数据边界。
2. 重排 `InstallView.vue` 模板为“总状态 → 主安装 → 目录诊断 → 辅助工具 → 维护危险区”。
3. 将现有 `SupportActions` 放入辅助工具区，保留其现有事件和更新协调器行为。
4. 统一安装、扫描、偏好、故障、账号和危险操作的进行中/成功/失败反馈。
5. 更新 `src/styles/main.css` 的安装页面样式，优先复用现有语义令牌，补齐 1100/860/640/375px 行为。
6. 增加页面行为测试：主 CTA 状态矩阵、目录扫描、安装禁用条件、备份选项、维护折叠和模态框提交。
7. 运行 `npm run typecheck`、定向 Vitest、`npm run lint`、`npm run build:web`。
8. 做静态布局验收：1440px、1024px、768px、640px、375px；浅色/深色/减少动效各一轮。

## 8. 验收门槛

- 未选目录、CS2 运行、安装中、已安装、失败和成功六种主状态均有明确主 CTA。
- 首屏能在不滚动的情况下看到当前结论、环境状态和安装主动作（小屏允许目录说明下移，但主 CTA 仍需可见）。
- 375px 无横向滚动、按钮文字不溢出、危险操作不与主安装动作混淆。
- 所有异步操作不会重复提交；错误有恢复动作或支持入口。
- 浅色/深色文本和边框对比度符合既有设计契约，颜色不是唯一状态信号。
- 现有 Tauri 安装、卸载、清理、故障提交、登录、更新和原版 Panel 行为测试不回退。
- 本次只完成 UI/交互重构；不扩大为安装包发布、真实 CS2 游戏验收、官网部署或资源包变更。

## 9. 调查来源

- 本地实现：`src/views/InstallView.vue`、`src/components/SupportActions.vue`、`src/components/StatusStrip.vue`、`src/styles/main.css`、`src/stores/cs2.ts`。
- 现有测试：`tests/ui-design-contract.spec.ts`、`tests/support-actions.spec.ts`、`tests/cs2-root-suggestions.spec.ts`、`tests/cs2-process-polling.spec.ts`。
- UI/UX Pro Max：桌面工具应优先使用清晰状态、错误恢复、加载反馈、键盘焦点、对比度和 375/768/1024/1440px 验收；Vue 层使用 Vue Test Utils 与 Pinia。
- Emil Design Engineering：高频 UI 交互使用短时、可打断的过渡；按钮提供即时按下反馈；不从 `scale(0)` 进入；只动画 `transform`/`opacity` 等低成本属性。
